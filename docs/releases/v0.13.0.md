# jpdev v0.13.0

This release has three parts:
- The release evidence gate gains a reported runner identity for standard GitHub-hosted runners ([issue #59](https://github.com/Judgment-Pack/judgment-pack-devkit/issues/59), [pull request #66](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/66)).
- An opt-in route lets a trusted branch reuse the evidence of the pull request that merged into it ([issue #60](https://github.com/Judgment-Pack/judgment-pack-devkit/issues/60), [pull request #67](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/67)).
- The assessment of version-pinned CI and release infrastructure is recorded with the maintainer's decision ([pull request #64](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/64)).

## Reported runner identity

The organization stays on standard GitHub-hosted runners. This is the maintainer's decision on #59, which takes the free-tier variant: no larger runners with custom images. The gate therefore pins what such a runner can show. This is a **reported** image identity, not a pinned VM image. The larger-runner direction stays recorded in the assessment as the route if the plan changes.

The new manifest is `templates/runner-identity.json`, version 1, revision 1, with `identity: "reported"`. It names five variants: `linux-x64`, `linux-arm64`, `macos-arm64`, `macos-x64` and `windows-x64`. A repository opts in with an `identity: {manifest, sha256}` member in `ci-evidence.json`. Each profile then names its `variant`, a `platform.ImageOS` pin and at least one tool.

The gate records and compares the following, always per variant and profile and never across unlike operating systems:
- `ImageOS` and `ImageVersion` as the runner reports them;
- `RUNNER_OS` and `RUNNER_ARCH`;
- the digest of the variant's OS-release file;
- the resolved tools;
- every `uses:` in the workflow, which must be pinned to a full commit or an image digest. A line that may spell the `uses` key in any other way refuses.

There are four new refusals:
- `identity-config`: the manifest is not the shipped, pinned revision, or a profile's platform is not its variant's.
- `identity-missing`: the identity record is absent, a field is missing, or no tools are recorded.
- `identity-unexpected`: another manifest, revision, variant or set of actions; an `ImageOS` other than the pin; another operating system or architecture; an `ImageVersion` such as `latest` or a wildcard; a malformed digest; or an unpinned action.
- `identity-changed`: the legs of one profile reported different images.

`identity-missing` and `identity-unexpected` are never revalidated. A rolled image against the release runner keeps v0.12.0's `runtime-identity` route.

Some dependencies are admitted without being read. `docs/ci-evidence.md` lists them:
- the inner `uses:` of remote composite actions and remote reusable workflows;
- `container:` and `services:` images;
- a local Docker action's `image:`.

## Pull-request-to-branch reuse

A repository opts in per workflow with `workflows.<key>.pull_request_reuse: {checks, environment}`. A branch job then runs `jpdev`'s `reuse` plan before its checks, and `capture --reuse-plan` records the covered checks as `REUSED`. Tree equality alone never qualifies. The gate binds the run through records that survive the merge and that the pull request's own code cannot write:
- **One pull request.** The head branch has had exactly one pull request ever: the merged one, from this repository.
- **No base change.** That pull request's timeline shows no base-change event of any kind. Every event name containing `base_change` or `base_ref` refuses.
- **The right run.** The run is at the pull request's final head, in this repository, with event `pull_request`, and was created after the pull request was opened.
- **The merge commit.** It has this commit's first parent and the pull request head as parents, and this commit's tree.
- **Same inputs.** Inputs, tools, images and the configured environment are equal. The checks step's environment is bound through `check.sh`'s new `JPDEV_BIND_ENV` line.
- **Coverage.** Only checks configured as reusable *and* passed in that run are covered.

The newest attempt is used whatever its result. A dispatch or a re-run never reuses. Every refusal makes the plan `fresh`, so the job runs its whole list. The refusal codes (`reuse-*`, `capture-plan`, `capture-merge`, `check-environment`) are listed in `docs/ci-evidence.md`. Without the opt-in, nothing about pull requests is read, and main-to-release reuse is unchanged. One code changed: a capture on a `pull_request` event without the opt-in now refuses `capture-event` where v0.12.0 refused `capture-ref`.

## `check.sh`

When `JPDEV_BIND_ENV` names variables, the template and the vendored copy print an `environment:` line in the summary block. The line holds the digest of the manifest read and of each named variable as the checks ran. Without the variable, the output is unchanged.

## Operating limits

- **Not live-tested.** The GitHub API reads behind the reuse binding (the head-branch listing, the timeline, the run fields) and the identity's runner variables were exercised only against fixtures modelled on read-only observations of this repository. The first live use is an adopting repository's first reuse decision, which should be watched.
- **Event names.** A future base-change event whose name contains neither `base_change` nor `base_ref` would not be refused.
- **No savings claimed.** No kit workflow adopts either feature, and nothing was timed.
- **Adoption** is each repository's own change, reviewed on its own pull request.
