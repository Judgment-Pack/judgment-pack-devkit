# jpdev v0.12.0

This release gives the release evidence gate a bounded route for the one refusal that the
hosted runner images now produce on their own: a rolled image between a repository's CI run
and its release job ([issue #60](https://github.com/Judgment-Pack/judgment-pack-devkit/issues/60),
[pull request #62](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/62)). It also
refuses a successful checklist status when log persistence leaves a selected check unrun
([issue #57](https://github.com/Judgment-Pack/judgment-pack-devkit/issues/57),
[pull request #58](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/58)), and the
policy names the two pre-release forms
([pull request #61](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/61)).

## The revalidation route

`ci-evidence.json` gains an optional `revalidation` member, `{"allowed": false}` by default and
when absent. When a publication passes every check of the gate and the only difference is the
release runner's image or tool identity against a `compare: release-runner` profile, an opted-in
repository gets the decision `revalidate` instead of `refuse`. Nothing else turns: a pin that does
not match, a newer failed or cancelled attempt, a moved tag, missing coverage, a changed input, an
expired run and a dispatch validation all refuse as before, and the identity check is the last
check of a job so any other refusal wins. The decision record carries `revalidation` with the
reason, the jobs concerned and, per drifting job, each differing key with its recorded and
release-runner values; `refusal` is null; the step output is `decision=revalidate`.

The route is a decision, not an admission. The release workflow acts on it by running the
repository's whole check list on the release runner, strictly, and publishing only when that run
succeeds. The kit's own `release.yml` does so: a `revalidate` job runs `check.sh --setup --strict`
and `check.sh --all --strict` on `decision == 'revalidate'`, and the package, attest and publish
jobs proceed on `reuse`, or on `revalidate` with that job's success, and on nothing else. The
"Revalidation" section of `docs/ci-evidence.md` carries the snippet and the bound.

The bound, stated: the fresh run is the check list `dev.json` declares, run strictly; work a CI
job does outside that list is not covered, so a repository whose evidence job does such work
either runs it in the release workflow (`fresh_at_release`) or does not opt in. A repository that
does not opt in decides exactly as before; its record gains the two `revalidation` members, and in
a multi-fault case the first refusal code reported can differ because the identity check moved
last (evidence with no `runtime` member now refuses `evidence-identity`).

## `check.sh --strict`

A step skipped because its `requires_env` variable is empty is a failure under `--strict`, whether
the step is optional or not and whether CI is set or not. The template and the vendored copy carry
it; the kit's revalidate job uses it.

## The checklist refusal

A checklist whose log persistence leaves a selected check unrun no longer reports success; the
status names the check that did not run.

## Operating limits

Those of v0.11.0. The route admits one refusal code under one opt-in; a repository that vendors
this version and does not set `revalidation.allowed` sees no change in decisions. Adoption in
another repository is that repository's own change, reviewed on its own pull request.
