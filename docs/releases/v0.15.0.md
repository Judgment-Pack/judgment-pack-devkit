# jpdev v0.15.0

This release completes the v0.15.0 milestone with one change:

- The release evidence gate gains a third compare mode, `release-os`. It holds the OS release and the exact tools, but not the image patch version ([#79](https://github.com/Judgment-Pack/judgment-pack-devkit/issues/79), [#80](https://github.com/Judgment-Pack/judgment-pack-devkit/pull/80)).

## The `release-os` compare mode

GitHub rolls a hosted image out in stages. During a roll, one runner label is served by several image versions at once. A profile with many parallel jobs, such as a sharded mutation table, then rarely lands on one image. `release-runner` needs every job to report the release runner's exact image. `pins` under the runner identity policy needs the jobs to report one image between them. Neither could pass, and re-running at the same commit draws the images again ([judgment-pack-agent#332](https://github.com/Judgment-Pack/judgment-pack-agent/issues/332)).

`"compare": "release-os"` is for evidence jobs whose result does not depend on the image patch version, given exact tools. It is available only under the runner identity policy. It holds:
- **Tools.** Every tool of the profile has a pin, and each job's recorded tools equal the pins exactly, as under `pins`.
- **OS release and platform.** The release job resolves the profile on its own runner before any evidence is read: the image name, OS, architecture and the digest of the variant's OS-release file, but not the tools. Each job must report exactly those values. Another image name, OS or architecture refuses `identity-unexpected`. Another OS-release digest, a tool that is not its pin, or another tool set refuses `runtime-identity`.
- **ImageVersion.** It must still have the form a hosted runner reports. It is recorded in each job's runtime and in two new members of the profile's identity group, `image_versions` (each job's) and `release_runner` (the image name and version, OS, architecture and OS-release digest the release runner resolved). It is compared with nothing: not with the release runner, and not among the profile's jobs.

Configuration refusals:
- `config-invalid` for a `release-os` profile without `identity`, or without a pin for every tool.
- `identity-config` for a variant with no OS-release file (`windows-x64`).
- A release runner that cannot resolve the profile refuses before any run is read (`runner-identity`, `runner-platform`, `identity-unexpected`, `identity-missing`).

**A difference is a refusal, never a drift.** It is not revalidated, even where `revalidation.allowed` is `true`, and it wins over a `release-runner` profile's drift. Revalidation reruns the check list `dev.json` declares on the release runner, and the work this mode is meant for (table shards, matrix legs with empty `checks`) is not that list. When a `release-runner` drift alone decides `revalidate`, a `release-os` job's evidence is taken as a `pins` leg's is, and the job is not in `revalidation.jobs`.

**What it gives up.** The mode is weaker than `release-runner`, and it is an adopter's explicit choice per profile:
- the jobs may run on different image patch versions of one OS release, with different preinstalled software outside the pinned tools;
- only the tools the profile names are bound, and only to their pins;
- the release runner does not run the profile's tools, so nothing shows that it could reproduce the jobs.

`docs/ci-evidence.md` has a new section, "The release-os mode". `docs/adopting.md` adds the choice to step 3 of the runner identity adoption, and the configuration template's comment names it.

## `release-runner` and `pins`

Both modes decide as before. All 167 earlier gate tests pass unchanged. A differential over the 114 earlier tests that drive the decision produced the same 340 decision records under the v0.14.0 gate and this one. Both the builder and the reviewer ran it; the reviewer first normalized the fixture archive digests, which carry their build time. The `pins` group keeps its record and its `identity-changed` wording.

In the code, `runtime()` is split into `runner_runtime()` (image and platform) and the tools, with the same refusals in the same order. The group rule moves into `identity_group()`.

## Operating limits

- **Not live-tested.** The mode was exercised against handwritten fixtures, and through the public command over a fixture repository with a stand-in `gh`. No repository has configured it yet. The first live use is an adopting repository's first release under it.
- **Every `release-os` profile is resolved first.** A `release-os` profile whose platform is not the release runner's refuses every release (`runner-platform`), even when no job names it.
- **The group rule is a backstop.** Through `verify`, the per-job checks refuse a differing job first, so `identity-changed` is not the code a release normally reports for this mode.
- **Adoption** is each repository's own reviewed change: re-vendoring the gate and choosing the mode per profile. This release re-vendors no consumer.
